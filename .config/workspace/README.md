# `.config/workspace/` — OceanCanvas runtime isolation for parallel checkouts

Lets the primary checkout (`/work/oceancanvas/main`) and any number of
Worktrunk streams (`/work/oceancanvas/worktrees/<stream>`) run at the same
time, next to other projects on the same workstation, without sharing host
ports, Compose projects, containers, networks or volumes.

The generic part lives in the workstation repo
(`agentic-ai-homelab/workstation/streams/`, "Workspaces"): `wb-workspace`
derives the identity (`WORKSPACE_*`, `COMPOSE_PROJECT_NAME`) and deterministic,
collision-checked ports, and the Worktrunk hooks call it. Everything
OceanCanvas-specific is here.

| File | Run by | Does |
|---|---|---|
| `setup` | `wb-workspace setup`: Worktrunk `pre-start` for a new stream; **by hand once in the primary** | Writes `compose/.env` (git-ignored, generated). Nothing else. |
| `teardown` | `wb-workspace teardown`: Worktrunk `pre-remove`, while the worktree still exists | Stops this checkout's Compose project; for a side stream, refuses on blocking root-owned files, then removes the project's volumes. |
| `test` | `bash .config/workspace/test` | Tests for both scripts and for the Compose / Makefile / Vite consumers. |

## Bootstrap (explicit; setup never installs anything)

Runtime versions come from the tracked `mise.toml` (Node 20) and
`.python-version` (Python 3.12, used by uv), so a fresh interactive shell in
any checkout resolves them. Per checkout:

```bash
cd pipeline && uv sync --extra dev --locked && cd ..
(cd gallery && npm ci)
(cd pipeline/src/oceancanvas/renderer && npm ci)
(cd e2e && npm ci)
```

Each checkout needs its own environment: `pipeline/.venv` is an editable
install with absolute paths into its own checkout (a copied venv would import
another checkout's source). About 0.4 GB `.venv` and 0.8 GB `node_modules`
per checkout. A non-interactive process with an older `PATH` may not see
`mise.toml`; compare `node --version` with `mise current node`, or use
`mise exec -- <cmd>`.

## `compose/.env` — the generated workspace configuration

Compose reads `.env` from the project directory, which for every
`docker compose -f compose/…` command is `compose/`, so the file applies
automatically; the repo-root `.env` (tracked, the pipeline's `env_file`) is
**not** read for this. The Makefile exports the same values to native targets
and `gallery/vite.config.ts` loads them with Vite's `loadEnv`.

```
# Generated by .config/workspace/setup for oceancanvas-<stream> — rerun 'wb-workspace setup' instead of editing.
COMPOSE_PROJECT_NAME=oceancanvas-<stream>
OC_GALLERY_PORT=…   OC_PREFECT_PORT=…   OC_RECIPE_PORT=…   OC_EXPORT_PORT=…   OC_VITE_PORT=…
PREFECT_HOME=<this checkout>/.prefect
```

- **Precedence:** shell environment > `compose/.env` > repository defaults.
  Setup warns when the shell already pins a different value.
- **Without the file** (CI, a plain clone): project `oceancanvas`, ports
  8080 / 4200 / 3001 / 3002 / 5173, exactly as before.
- **Ownership:** the first line carries the generated-file marker; setup
  refuses to overwrite a `compose/.env` without it, and refuses to write one
  that isn't git-ignored (it would block `wb-integrate`).
- Written atomically; a rerun with the same result leaves the file untouched.
- **Never secrets.** See "Secrets".

## Ports

Every checkout configured through `wb-workspace setup` — the primary
included — gets its ports from `wb-workspace port`: deterministic per
`<project>/<stream>/<slot>`, range 10000–19999, collision-checked against every
Model-B checkout's same slots; a collision stops setup (rename the stream).
This is what lets the OceanCanvas primary run next to Orrery's (both
projects' plain defaults are 8080).

| Slot | Variable | Default | Used by |
|---|---|---|---|
| `gallery` | `OC_GALLERY_PORT` | 8080 | Compose `gallery` (Caddy) host port; Vite proxy for `/data`, `/renders`, `/sketches`, `/audio`, recipe YAML; `make screenshots` |
| `prefect` | `OC_PREFECT_PORT` | 4200 | Compose `prefect-server` UI host port |
| `recipe-api` | `OC_RECIPE_PORT` | 3001 | Compose `recipe-server` host port; native save server (`make gallery-dev`); Vite `/api` proxy |
| `export-api` | `OC_EXPORT_PORT` | 3002 | Compose `export-server` host port; native export server (`make gallery-dev`); Vite `/api/export` proxy |
| `vite` | `OC_VITE_PORT` | 5173 | Vite dev server, **strict** when set: it fails instead of drifting to another port |

Services reach each other by Compose service name, never through these host
ports. The e2e stack (`compose/docker-compose.test.yml`) publishes nothing:
Playwright reaches the gallery over the Compose network, so `make e2e` needs
no slot and two checkouts can run it at once. Postgres is never published.

The native dev loop (`make gallery-dev`) still expects something serving data
on the gallery port: the Docker gallery (`make up`) or
`python3 -m http.server "$OC_GALLERY_PORT"` (values: `cat compose/.env`).
Running `make up` and `make gallery-dev` together in one checkout conflicts on
the recipe/export ports, as it always has.

## Docker Compose

Both Compose files set `name: oceancanvas` (the default) and no
`container_name`, volume `name:` or image tag, so Compose scopes everything to
the project: containers `<project>-<service>-1`, network `<project>_default`,
volumes `<project>_pgdata` / `_test-processed` / `_test-renders`, built images
`<project>-pipeline` / `-gallery` / `-e2e`.

The production and e2e stacks share one project name per checkout (CI builds
once and reuses the images). So `make e2e`'s `down -v --remove-orphans` also
stops a production stack running **in the same checkout**; other checkouts are
unaffected.

## Teardown

| Checkout | Does |
|---|---|
| any | `docker compose -p $COMPOSE_PROJECT_NAME down --remove-orphans` (containers, network) |
| side stream | root-owned residue check (below), then `docker compose -p $COMPOSE_PROJECT_NAME down --remove-orphans --volumes` |
| primary | volumes and images kept |

Every Docker operation is one Compose command scoped by `-p`; teardown builds
no label filter, name pattern or ID list of its own. All OceanCanvas volumes
are disposable (Prefect bookkeeping, e2e outputs; pipeline data and renders
live in the checkout, not in volumes). No Docker or no daemon counts as
nothing to stop. Never a prune, never another project.

### Images

Teardown never removes images. A side stream leaves its built images behind
(about 6.6 GB: e2e 3.8 GB, pipeline 2.7 GB, gallery 0.1 GB); list them with
`docker image ls --filter label=com.docker.compose.project=<project>` and
remove them by name if needed. Image maintenance belongs to the workstation's
later storage/maintenance phase. Image removal was taken out of teardown after
the incident below: correctness and cross-project safety come before automatic
disk reclamation.

### Root-owned residue

Containers run as root and write into bind mounts (`data/`, `renders/`,
`recipes/`, `pipeline/tests/fixtures/`). Deleting an entry needs write
permission on its parent directory, so a root-owned directory with contents
would make the worktree removal fail partway. A side stream's teardown lists
every path there that isn't owned by you; if any is blocking, it **fails**
(which stops `wt remove`) and keeps the worktree, removing nothing else.
Root-owned files in your own directories are removable and only reported.
Nothing is ever chowned. Recover by deleting the listed paths as root from a
container (the message prints the command), then rerun teardown. `make e2e`
alone leaves only removable residue (`pipeline/tests/fixtures/recipes/e2e-save-test.yaml`);
the production pipeline (`make up` / `make pipeline-run`) creates root-owned
directories under `renders/` and `data/`.

## Secrets: none, and never copied

OceanCanvas needs no secrets (no-auth sources). The tracked root `.env` holds
non-secret configuration and reaches every checkout through Git; setup never
writes, copies or links it. The optional Sentry DSN (`SENTRY_DSN`,
`VITE_SENTRY_DSN`) goes in the shell environment only, never in a tracked
file.

## Testing destructive scoping

**Production scoping and test-harness scoping are separate safety layers.** A
test designed to validate destructive scoping must not be capable of causing
cross-project damage merely because the implementation under test has exactly
the scoping defect the test is trying to detect. This applies to images,
containers, networks, volumes and any future destructive workspace cleanup.

The incident that taught it (2026-10-15, Slice 5): a mutation test of an
earlier teardown widened its image selector from this Compose project to every
Compose-labelled image, and the harness ran that broken copy against the
shared workstation daemon. It deleted two unused Orrery images
(`orrery-x3-runtime-smoke-web`, `orrery-docker-e2e-web`) and three unused
OceanCanvas ones; Docker only spared images in use by a running container. The
suite still passed: its only foreign image belonged to a running container, so
Docker itself refused the deletion and masked the broken selector.

`test` therefore:
1. runs contract and mutation tests against a fake `docker` that records its
   arguments, with `DOCKER_HOST` pointing at a nonexistent socket (the real
   daemon is unreachable even via the absolute binary); deliberately broken
   copies run only there;
2. runs only the unmodified teardown against the real daemon, behind a guard
   shim independent of it that allows `docker info` and
   `docker compose -p oc-wstest-<pid>-<x> down [--remove-orphans] [--volumes]`
   and refuses anything else (and proves that with probes on nonexistent names);
3. snapshots every container, image, volume and network outside the
   `oc-wstest-<pid>-` namespace before and compares after;
4. includes an unused foreign Compose-built image (no container at all) that
   must survive teardown, closing the assertion gap;
5. cleans its own fixtures by exact namespaced names only.

## Known limitations (OceanCanvas)

Generic workstation limitations are listed once in
`agentic-ai-homelab/workstation/DEVELOPER-SETUP.md` ("Known limitations").
OceanCanvas's own:

- **Images accumulate** per stream (see "Images"); remove by name, never prune.
- **Dependencies per stream**: about 1.2 GB per checkout, installed by hand.
- **Root-owned residue** from the production pipeline blocks a side stream's
  teardown until removed by hand (by design: detection, no automatic chown).
- **Shared runtime cost in one checkout**: `make up` + `make gallery-dev` and
  `make up` + `make e2e` interfere inside the same checkout (unchanged behaviour).
- `docker-compose.dev.yml` is an unused override fragment; it has no
  `name:` and isn't wired into any make target.
